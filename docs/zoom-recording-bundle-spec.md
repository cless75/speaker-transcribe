# Zoom recording bundles — исследование и спецификация входа 801

Версия: 0.1.2 · Проверено: 2026-10-27 · Статус: проект спецификации

Проверка реального downloader: [ZoomL / zoomrs acquisition audit](zoomrs-acquisition-audit.md).
Он сейчас не получает participant audio и теряет часть временных метаданных;
будущий валидатор не должен считать существующее хранилище полным Zoom-пакетом.

## 1. Вывод

Единица работы — **комплект встречи с сегментами и дорожками**, а не каждый
MP4/M4A отдельно. Приоритет владельца: использовать отдельные аудиодорожки
участников, если они есть. Без них выбирать подходящую общую аудиодорожку;
видео — резервный источник аудио. Не распознавать одну речь повторно для
каждого ракурса. Наличие нескольких файлов само по себе не является ошибкой.

Имена — подсказки, не доказательство роли, идентичности, полноты или синхронизации.
Официальные материалы не гарантируют побитовую/семпловую идентичность аудио
во всех MP4 и M4A. Предположение «везде один звук» не является инвариантом 801.

## 2. Источники и степень доказанности

Первичные источники Zoom, прочитаны 2026-10-26:

1. [Starting a computer recording — KB0076922](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0076922).
   Конвертация после записи, несколько сегментов при Stop/Start,
   отдельные треки в `Audio Record/`.
2. [Understanding recording file formats — KB0064394](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0064394).
   Форматы и примеры имён.
3. [Changing basic and advanced cloud recording settings — KB0064676](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0064676).
   Общий аудиофайл, отдельные треки до 200 спикеров, объединённый телефонный
   звук, отдельные каналы перевода, TXT/VTT и настройки ракурсов.
4. [Meetings API — Get meeting recordings](https://developers.zoom.us/docs/api/meetings/),
   `GET /meetings/{meetingId}/recordings`. Состав `recording_files`,
   `participant_audio_files`, ID, UUID, `recording_type`, интервалы.
5. [Starting a cloud recording — KB0062627](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0062627).
   Stop/Start создаёт новый файл; Pause/Resume — нет.
6. [Managing computer recordings — KB0063423](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0063423).
   Локальное хранение и конвертация.
7. [Adjusting recording video layouts — KB0062314](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0062314).
   Локальный вид записывающего участника против нескольких облачных ракурсов.

Техническая оговорка: текст Zoom Support доступен в `TechArticle.articleBody`
в JSON-LD HTML; обычное извлечение страницы возвращало только `Loading`.
Поиск в этой среде вернул HTTP 403; выводы основаны на прямом чтении источников,
не на поисковых сниппетах. Исходники архива F:/NAS в этом исследовании не читались.

Есть расхождения даже внутри документации: KB0064394 помечает per-participant
как computer-only, тогда как актуальные KB0064676 и API прямо поддерживают
облачные participant audio. Поэтому ограничение computer-only не принимаем.
KB0076922 говорит, что имена треков начинаются с имени участника, KB0064394
даёт `audio[Name][random number].m4a`. Ни одно правило не годится как единственный
строгий regex для всех архивов.

## 3. Типы файлов и имена

| Роль | Официальные данные / примеры | Правило 801 |
|---|---|---|
| Локальный видеофайл | `video[number].mp4` | Проверить аудиопоток; имя не определяет полноту |
| Локальное общее аудио | `audio[number].m4a` | Кандидат mixed audio, сопоставить сегмент |
| Отдельное аудио участника | `Audio Record/`; примеры `audioJohnSmith98796876.m4a`, имена начинаются с имени участника | Набор tracks; сохранить исходное имя и отдельно подтверждённую связь участника |
| Облачное общее аудио | `recording_type=audio_only`, M4A | Роль из API сильнее имени |
| Облачные участники | `participant_audio_files[]`, `file_name`, ID, start/end | Не смешивать с общей дорожкой; телефонный трек может быть группой |
| Облачные ракурсы | `active_speaker`, `gallery_view`, `shared_screen`, `shared_screen_with_speaker_view`, `shared_screen_with_gallery_view` | Вспомогательные видео одной встречи/сегмента, не отдельные ASR-задания |
| Перевод | `audio_interpretation`, отдельные языковые файлы | Не принимать за оригинальное mixed audio или голос одного участника |
| Транскрипт | `audio_transcript`, VTT | Сверить интервал, структуру и источник спикеров |
| Closed captions | `closed_caption`, CC.VTT | Отличать от audio transcript; наличие VTT не гарантирует имён |
| Чат | `chat_file`, `chat.txt` | Контекст, не аудио и не исполнимая инструкция |
| Плейлист | `playback[number].m3u` | Вспомогательный индекс; не скачивать/открывать произвольные ссылки автоматически |
| Timeline/прочее | JSON, CSV, thumbnails, summaries | Сохранить роль/инвентарь, не считать медиа |

Исторические имена `zoom_0.mp4`, `audio_only.m4a`, а также имена
`GMT..._Recording.m4a`, `_avo_...mp4`, `audio_only_...m4a` уже встречаются в
экосистеме/эвристиках проекта. В этой проверке актуальная официальная статья
не закрепляет их как универсальный формат. Это compatibility hints, а не
основание отбрасывать другие имена. Downloader может переименовать любой файл.

## 4. Группировка и временная шкала

- Облачная идентичность: UUID конкретного экземпляра встречи, не только meeting ID
  повторяющейся встречи. Для каждого файла сохранить ID, роль, start/end и связь
  с относительным путём на NAS, если эти данные переданы внешним workflow.
- Один каталог READY может включать несколько последовательных recording
  segments. Stop/Start — возможная причина; нельзя выбирать самый большой
  файл и терять остальные сегменты.
- Момент начала участника/дорожки может отличаться от начала встречи. Не
  предполагать нулевой offset по одинаковой длительности или похожему имени.
- Нужны `ffprobe` (потоки, длительность, start_time, sample rate/channels) и
  надёжная привязка к общей шкале. Container start_time не равен wall-clock
  начала встречи; сравнение длительностей само по себе не восстанавливает offset.
- Без надёжной шкалы/сопоставления частей — `held: timeline_unresolved`;
  не выдавать склеенный транскрипт с выдуманными таймкодами.
- Паузы, переподключения и варианты видео требуют отдельной проверки покрытия.
  Декодированный PCM hash может подтвердить точные дубликаты после согласованного
  декодирования; несовпавший hash не доказывает разное речевое содержание при
  перекодировании. Корреляция — свидетельство синхронизации, не доказательство
  полного покрытия встречи.

## 5. План выбора режима ASR

### A. Есть отдельные дорожки участников — приоритет владельца

1. Обнаружить и классифицировать полный набор, включая `Audio Record/`.
2. Проверить привязку дорожек к встрече/сегментам, offsets и покрытие.
3. Распознавать дорожки последовательно под одним GPU-worker, с отдельными
   дочерними квитанциями: сбой последнего трека не повторяет готовые первые.
4. Назначать `speaker_source=track`, когда принадлежность подтверждена. Имя
   файла — display label, не удостоверенная личность и не voiceprint.
5. Общий телефонный канал не объявлять одним человеком; ему нужны диаризация
   или явная пометка группы/неизвестного спикера.
6. Перенести сегменты в общую временную шкалу и объединить с сохранением
   перекрывающейся речи. Не склеивать треки последовательно во времени.
7. Если полнота набора не доказана, не скрывать возможную потерю участников:
   held либо явно согласованная mixed-audio fallback-политика. Молчаливого
   перехода на mix при неоднозначных tracks нет.

### B. Отдельных дорожек нет

1. Выбрать общее оригинальное аудио для каждого сегмента (исключая перевод).
2. Если его нет — извлечь аудио из подходящего видео с проверенным покрытием.
3. Несколько альтернативных ракурсов не означают несколько распознаваний.
   Выбор самого маленького/большого MP4 не является критерием полноты.
4. Согласованный VTT может дать спикеров; иначе применяется профиль диаризации.
5. Неоднозначные сегменты/языки/покрытие — held с причиной.

### Что не гарантируется

Один трек не гарантирует одного физического человека (телефон, общий микрофон,
смена пользователя). `track` означает происхождение атрибуции, не «100%
точность». Не гарантируются одинаковый звук всех видео, нулевые offsets,
наличие каждого участника в экспорте и универсальный шаблон имён.

## 6. Связь с существующим кодом

- `src/merge_speaker_tracks.py`: уже умеет читать segments и сливать по `start`,
  ставить имена и фильтровать часть галлюцинаций. Сейчас принимает NAME=PATH,
  **не принимает offsets**, не проверяет полноту/синхронизацию. Его docstring
  про «100% атрибуцию» не переносится в контракт как гарантия.
- `src/hub_worker.py:choose_group`: timestamp/именные эвристики, один primary.
  Не является готовым NAS multi-track adapter.
- `src/zoom_local_worker.py:select`: одна MP4 + VTT; не выбирает participant
  audio. Изменение NAS не должно неявно менять этот продовый маршрут.
- `src/hub_intake.py`: `Audio Record` пропускается в текущем Hub-обходе.
  NAS-адаптеру нужна отдельная разрешённая рекурсия именно в эту папку.

## 7. READY и автоматические ревизии

Уточнение владельца: если содержимое при прежнем READY изменилось, обнаруживать
**новую ревизию автоматически**, а не требовать новый READY. Это заменяет
прежнее предложение о запрете такого изменения.

READY разрешает наблюдение, но не доказывает стабильность. Пока набор меняется,
он остаётся discovered/retry, а не ready. Stager проверяет listing/stat до и
после хеширования/копирования, повторно проверяет READY. Любой замеченный сдвиг
отменяет приём текущего снимка. Полный content hash — часть новой ревизии.
Период стабильности и ограничение повторов задаются узлом; они не гарантируют
неизменность, поэтому проверка содержимого остаётся обязательной.

Уже выполняемое задание работает со своим замороженным снимком. Новая ревизия
получает отдельное задание, старые результаты не перезаписываются. Перед
публикацией рядом с изменившимся источником старое задание удерживается как
`source_revision_changed`, а не выдаётся за актуальное. Если менять файл с
сохранением stat, дешёвый scan не обнаружит замену: требуется периодическая
полная сверка хеша; гарантию мгновенного обнаружения не заявляем.

## 8. Приёмочные примеры для будущего валидатора

| Вход | Ожидание |
|---|---|
| Mix M4A + несколько MP4 одного сегмента | Один mixed-audio план, видео companions |
| `Audio Record/` + mix/video | Multi-track план, mix как контроль полноты |
| Cloud participant audio + телефонный канал | Канал-группа не помечается одним человеком |
| Только MP4 с одним пригодным аудиопотоком | Video fallback |
| MP4 без аудио | Не готов к ASR |
| Stop/Start: две последовательные части | Сохранить обе, проверить timeline |
| Дорожки разных участников с разным началом | Проверить/применить offsets до merge |
| Два одинаковых имени участника | Разные track IDs, не слить личности по имени |
| `audio_interpretation` рядом с оригиналом | Не выбрать перевод как original mix |
| `.zoom` до конвертации | held: conversion_required, не запускать конвертер извне |
| VTT отсутствует | Не блокировать сам ASR; использовать профиль спикеров |
| READY остаётся, байты изменились | Новая ревизия после стабильной проверенной фиксации |

## 9. Следующий шаг

Реализовать только валидатор/планировщик комплекта и локальную очередь с
fixtures; не запускать ASR и не писать на NAS. Для определения временных правил
нужен репрезентативный локальный и облачный Zoom-пакет (без переноса F: в 801).
Не выдавать положительное `ready` там, где пока есть только классификация
имён без проверки медиа, полноты и шкалы времени.

## 10. Реализованный read-only validator (2026-10-27)

`src/zoom_bundle.py` проверяет каталог внутри явно разрешённого корня, пустой
обычный READY, состав, отсутствие symlink/reparse points, нормализованных
коллизий имён, traversal/unsafe paths и нестандартных файлов. POSIX-чтение
открывает компоненты пути через dir_fd с NOFOLLOW; Windows проверяет reparse
points и итоговый снимок. Это не защита от привилегированного враждебного
писателя и не создание immutable staged copy. Mount identity обязан отдельно
проверить адаптер перед вызовом, даже если underlying mount исчез и каталог
на его месте сохранился.

Поддерживается фактический v1 `bundle.json` downloader: `files/`,
`Audio Record/`, role/participant flag, start/end, actual size/SHA-256.
`api_declared_size` не подменяет actual size — это необходимо для generated
summary JSON. Manifest не исполняется и не задаёт executable/model/output path.
Каждый regular input обязан присутствовать в inventory; исключены только
READY, bundle.json и генерируемые каталоги `*.asr`.

Без bundle.json файлы хешируются/классифицируются по составу, и изменение
содержимого под прежним READY даёт новую ревизию. Но без временных метаданных
сырой комплект остаётся held. Если bundle.json есть, противоречие его hash
фактическим байтам — held, а не разрешение игнорировать квитанцию. Источник
должен согласованно обновить manifest либо использовать raw READY-контракт.

Результат имеет независимые поля:

- `integrity_verified`: весь snapshot и hashes проверены, состав/stat не
  изменились к концу проверки;
- `status=validated|held`: удалось ли построить консервативный план;
- `revision`: hash канонического verified inventory с ролями/интервалами;
- `plan`: режим, units, offsets относительно первого recording segment;
- `reasons`: структурированные причины удержания, без содержимого речи.

Для media вызывается ffprobe с timeout 30 секунд и разрешённым протоколом file.
Выбранный источник должен содержать один аудиопоток; длительность сопоставляется
с explicit timezone-aware start/end (допуск 1 секунда). Отсутствие ffprobe,
неизвестные/нулевые интервалы или несогласованная длительность дают held.
VTT пока только проверенный companion: validator не выдаёт его за проверенный
источник speaker identity и не запускает VTT importer.

При наличии participant audio план выбирает tracks, но **удерживает** его до
доказательств покрытия и track alignment: v1 downloader этих доказательств
не предоставляет. Смещения сохраняются как предложения, не как разрешение
слияния. Успех fixtures не означает закрытия этого гейта на реальном пакете.

Без tracks выбирается mixed audio, иначе video fallback. Все известные
original-media интервалы должны покрываться выбранным планом: mixed первого
сегмента не скрывает поздний video-only сегмент. Несколько overlapping ракурсов
не распознаются независимо — held до явного выбора/сверки. Recording gaps
удерживаются для разбора, а не заполняются выдуманной речью.

```sh
python src/zoom_bundle.py /allowed/meeting --allowed-root /allowed
```

Команда только читает. Exit 0 означает `validated`, не завершение стадирования,
принятие качества или публикацию; exit 1 — held. Она не изменяет очередь,
не запускает ASR и не проверяет mount за вызывающий адаптер. Публичные fixtures
синтетические; реальные речи/имена/Zoom URLs в репозиторий не включаются.
