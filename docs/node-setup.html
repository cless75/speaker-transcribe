Развёртывание ASR-узла
распознавание речи + диаризация

Пошаговая инструкция по установке узла транскрибации с диаризацией спикеров и пер-проектным voiceprint на новой Windows-машине. Узел работает как headless-обработчик: читает источники, делает ASR на GPU, складывает результаты в общий Hub.

Windows 10/11 NVIDIA CUDA 12.8 Python 3.11 faster-whisper + pyannote self-contained

iО документе

Этот файл лежит в репозитории и открывается локально (один HTML-файл, без внешних зависимостей). Он проведёт от чистой машины до работающего узла, который участвует в распределённой обработке записей.

Принцип: код публичный — данные приватные. В этой инструкции все токены, пути и имена — плейсхолдеры. Подставляйте свои значения локально. Никогда не коммитьте реальные секреты, голосовые отпечатки, транскрипты и имена в репозиторий. Голос = биометрические персональные данные; он живёт только в вашем приватном Hub. Подробнее — раздел Приватность.
Плейсхолдеры в командах: <...> — заменить на своё; {cache_root}, {hub_root} — корни путей вашей машины.

⚡Быстрый путь: установка через AI-агента

если на машине уже есть Claude Code или Codex

Если у вас установлен Claude Code или Codex (либо другой агент с доступом к терминалу) — не копируйте команды вручную. Делегируйте установку агенту: он сам адаптируется к вашему железу (GPU, диски, пути), обработает типовые затыки (ExecutionPolicy, PATH, cuDNN) и доложит результат каждого гейта. Дайте агенту такой промпт:

Установи speaker-transcribe на эту машину (Windows, NVIDIA CUDA).

1. Поставь Git (winget Git.Git) и Python 3.11 (winget Python.Python.3.11), если их нет.
2. Склонируй https://github.com/cless75/speaker-transcribe в C:\work\speaker-transcribe
3. Следуй docs/node-setup.html: venv в C:\work\venvs\asr; torch 2.11.0 + torchaudio 2.11.0
   из индекса https://download.pytorch.org/whl/cu128; затем pip install -r requirements.txt;
   nvidia-cudnn-cu12; ffmpeg (winget Gyan.FFmpeg).
4. Вызывай venv python напрямую (C:\work\venvs\asr\Scripts\python -m pip ...) — без активации,
   чтобы обойти PowerShell ExecutionPolicy.
5. Проверь гейты и доложи: nvidia-smi видит GPU; torch.cuda.is_available() == True;
   оба smoke-теста (PYTHONUTF8=1) зелёные.

Среда: только диск C:. GPU — внешняя NVIDIA RTX 3050 (eGPU). Движок CUDA-only.
Агент пройдёт те же шаги, что в разделах ниже, но без ручного копирования. Дальше (токены, конфиг, режимы) — там же. На macOS уточните агенту: CPU-профиль (int8), без CUDA/cuDNN, ffmpeg через brew (см. секцию macOS).

3Python-окружение

~15–25 мин · venv + зависимости + cuDNN + ffmpeg

3.1 · Установить Python 3.11 (если нет) и создать venv

:: проверить наличие 3.11 (системный может быть другой версии)
py -3.11 --version
:: если нет — поставить, затем открыть НОВОЕ окно терминала:
winget install --id Python.Python.3.11 -e

:: создать venv
py -3.11 -m venv C:\work\venvs\asr

:: --- ВАРИАНТ A (рекомендуется): без активации, вызывать venv python напрямую ---
::     работает всегда, не зависит от политики выполнения скриптов
C:\work\venvs\asr\Scripts\python -m pip install -U pip wheel setuptools

:: --- ВАРИАНТ B: активировать venv, чтобы потом писать просто pip/python ---
::     PowerShell по умолчанию блокирует .ps1 → сначала разрешить для текущей сессии:
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
C:\work\venvs\asr\Scripts\Activate.ps1
::     в cmd.exe вместо двух строк выше: C:\work\venvs\asr\Scripts\activate.bat
Две частые ошибки на Windows:
• pip «не распознано» — venv не активирован; глобального pip в PATH обычно нет.
• «выполнение сценариев отключено в этой системе» — PowerShell блокирует Activate.ps1.
Простое решение для обоих: используйте Вариант A — вызывайте C:\work\venvs\asr\Scripts\python -m pip ... напрямую (далее в инструкции команды с pip подразумевают активированный venv либо этот полный путь).
Именно 3.11 — у pyannote/torch есть готовые бинарные колёса под него; на самых новых интерпретаторах pip может полезть собирать из исходников (медленно, часто падает на Windows).
Когда активация НЕ нужна: активация venv — это лишь удобство для интерактивных команд установки (чтобы писать короткое pip/python). Для запуска самого движка активация не требуется — интерпретатор берётся из явно заданного пути:
  • CLI / watcher — поле transcribe_python в конфиге (шаг 5);
  • PowerShell-обёртка — параметр -PythonBin;
  • режим агента (MCP) — переменная TRANSCRIPTION_PYTHON.
Поэтому автозапуск/планировщик/сервис работают без активации — указывайте полный путь к ...\venvs\asr\Scripts\python.exe.

4Токены

для диаризации нужен HF_TOKEN; для чистого ASR — не нужен

Распознавание спикеров (диаризация) использует закрытые модели pyannote и требует токена Hugging Face. Подробная пошаговая инструкция получения — на отдельной странице: → Получение токена Hugging Face.

Кратко — задайте токен в переменной окружения (код читает HF_TOKEN):

:: PowerShell — на текущую сессию:
$env:HF_TOKEN = "hf_ВАШ_ТОКЕН"
:: постоянно (новые окна):
setx HF_TOKEN "hf_ВАШ_ТОКЕН"
:: на уровне машины — видна под любым юзером и после перезагрузки (нужен admin-шелл):
[Environment]::SetEnvironmentVariable("HF_TOKEN","hf_ВАШ_ТОКЕН","Machine")
Для узла с scheduled task ставьте переменную на уровне Machine: setx пишет её только текущему пользователю, а задача выполняется под своим владельцем (см. Диагностика, секция [7]) — под ним user-scope переменной просто нет.
Env-переменная надёжнее CLI-логина: не зависит от наличия huggingface-cli и переживает пересоздание venv. Для чистого теста ASR (--speaker-mode off) токен не нужен вовсе.
Никогда не коммитьте токен в репозиторий и не кладите в публичные папки/Hub.

6Первый запуск

реальная транскрибация одного файла на GPU

Положите короткий тестовый файл (.m4a/.mp4) и прогоните чистый ASR — без диаризации, токен не нужен:

:: PYTHONUTF8 — корректный вывод кириллицы (иначе UnicodeEncodeError на cp1251)
set PYTHONUTF8=1
C:\work\venvs\asr\Scripts\python src\media_transcribe_cli.py --input C:\work\test.m4a --output-dir C:\work\output --model medium --speaker-mode off
Первый запуск качает модель. faster-whisper при первом прогоне скачает выбранную модель в кэш (medium ≈ 1.5 ГБ, large-v3 ≈ 3 ГБ) — это разовая загрузка, может занять несколько минут. Дальнейшие запуски стартуют сразу. Аналогично pyannote качает модели диаризации при первом --speaker-mode on.
Успех: в C:\work\output появился *-transcript.md с текстом — движок работает на GPU.
Ложный сбой: прогон может рапортовать exit 9 (teardown CUDA) при фактическом успехе — судите по наличию transcript.md, а не по коду возврата.
С распознаванием спикеров — добавьте --speaker-mode on (нужен HF-токен). Удобнее — обёртка transcribe.ps1 (см. Быстрый запуск).

7Автозадача: вотчер по расписанию

headless-режим: узел сам разбирает очередь каждые N минут

До сих пор всё запускалось руками. Чтобы узел работал сам, вотчер вешают на Task Scheduler: задача раз в N минут делает один прогон (watch.ps1 -Once) — сканирует источники, забирает новые файлы, пишет транскрипты в Hub и дописывает logs\watch.log.

7.1 · Регистрация

Скрипт сам находит пути (репозиторий может лежать где угодно) и требует прав администратора — регистрация задачи без них невозможна:

:: PowerShell ОТ АДМИНИСТРАТОРА, поднятый из-под узлового юзера
cd C:\work\speaker-transcribe
.\scripts\install-watch-task.ps1 -IntervalMinutes 10

Либо правый клик по scripts\install-watch-task.cmd → «Запуск от имени администратора» (файл сам поднимет права через UAC).

Из-под какого юзера поднят admin-шелл — тому задача и достанется. Скрипт регистрирует её на $env:USERNAME своего шелла (-LogonType Interactive). Если повысить права другой админ-учёткой, задача уйдёт ей — а у неё нет ни примонтированного облачного диска, ни venv узла, и вотчер будет молча падать. Разбор симптома — задача есть, узел молчит.

7.2 · Параметры

ФлагЗначение
-TaskNameимя задачи; по умолчанию speaker-transcribe-watch
-IntervalMinutesпериод прогонов, по умолчанию 10
-Configпуть к конфигу; по умолчанию <repo>\config\node.local.json
-PythonBinvenv-python для прогонов; без него используется значение по умолчанию из watch.ps1
-LogDirкаталог для watch.log; по умолчанию <repo>\logs
-NoAutoUpdateотключить самообновление: по умолчанию каждый прогон сначала делает git pull --ff-only
-Removeудалить задачу

7.3 · Что задача делает на самом деле

  • триггер при входе пользователя + повтор каждые N минут без ограничения длительности;
  • работает только пока юзер залогинен — иначе облачный диск не смонтирован и Hub недоступен;
  • параллельные прогоны запрещены (IgnoreNew): новый прогон не начнётся, пока идёт предыдущий;
  • упавший прогон перезапускается до 3 раз с интервалом 2 минуты;
  • весь вывод дописывается в logs\watch.log — по нему и судят о жизни узла.
Самообновление. По умолчанию задача каждый прогон подтягивает свежий код (git pull --ff-only, best-effort). Поскольку параллельные прогоны запрещены, обновление всегда происходит между прогонами, а не посреди обработки файла.

7.4 · Проверка

:: запустить прямо сейчас, не дожидаясь интервала
Start-ScheduledTask -TaskName speaker-transcribe-watch
:: состояние и результат последнего запуска
Get-ScheduledTaskInfo -TaskName speaker-transcribe-watch
:: живой лог
Get-Content .\logs\watch.log -Tail 20 -Wait
Успех: в логе появляются строки sweep start (host=…) и queue empty; nothing more to process, а LastTaskResult равен 0.

Одной командой «жив ли узел вообще» отвечает health-проверка — она смотрит задачу, свежесть лога, доступность Hub, наличие токена и состояние очереди:

.\scripts\watch-health.ps1
:: код возврата: 0 = OK, 1 = деградация (лог протух, истёк claim), 2 = не работает
watch.log пишет только задача. Ручной watch.ps1 -Once печатает в консоль и в лог не попадает — не пугайтесь «пустого» лога после ручного прогона.

7.5 · Удалить или пере-регистрировать

:: удалить (из admin-шелла того юзера, которому задача принадлежит)
.\scripts\install-watch-task.ps1 -Remove
:: посмотреть ВСЕ задачи вотчера, включая чужие (нужен admin)
Get-ScheduledTask | Where-Object {
  ($_.TaskName -match 'watch|transcribe|audio') -or
  ((($_.Actions | ForEach-Object { "$($_.Execute) $($_.Arguments)" }) -match 'watch\.ps1|audio_inbox_watch'))
} | Select-Object TaskPath, TaskName, State, @{n='User';e={$_.Principal.UserId}}
:: снести лишнюю по имени
Unregister-ScheduledTask -TaskName '<имя>' -Confirm:$false
Две задачи на один узел — это не удвоенная скорость, а конкуренция за очередь. Прежде чем регистрировать новую, убедитесь, что старой (в том числе под другим юзером и под старым именем) не осталось. Перечисление задач урезается правами, поэтому проверять надо из-под администратора.

7.6 · Чтобы узел пережил перезагрузку

Задача с триггером «при входе» оживёт только если в систему кто-то вошёл. Для узла, который должен подниматься сам:

  1. Авто-логин узлового юзера — Sysinternals Autologon (пароль хранится LSA-шифрованным) или netplwiz. Это осознанный размен: физический доступ к машине = доступ к сессии.
  2. Облачный диск при старте — включить «запускать при входе в систему» и убедиться, что точка монтирования совпадает с hub_root в конфиге.
  3. Секреты не в пользовательском scope — переменная уровня Machine либо файл в Hub ("secrets": { "hf_token": "file:{hub_root}/_meta/.hf-token" }), иначе задача их не увидит.
  4. Машина не должна засыпать:
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
Переключаясь на другого пользователя, выбирайте «Сменить пользователя», а не «Выход»: при смене сессия узла остаётся жить — диск смонтирован, задача продолжает тикать. «Выход» уничтожает сессию, и узел молчит до следующего входа.

⛓Схема работы

Что движок делает с файлом — от входа до транскрипта:

Вход — медиафайл, локальная папка или Hub-источник
ffmpeg — извлечение аудиодорожки из аудио/видео
Чанкинг — длинное аудио → куски с перекрытием
ASR — faster-whisper на CUDA → текст с таймкодами
Диаризация — pyannote → кто и когда говорил
Voiceprint (опц.) — ECAPA-TDNN → идентификация известных голосов
Выход — *-transcript.md + сегменты (jsonl/vtt) + state.json (для Hub)

▸Режимы запуска

логика ASR общая — различается оркестрация и источник файлов

Движок используется тремя способами — спектр от оркестрации к простоте: через AI-агента, напрямую из командной строки или просто складывая файлы в локальную папку. Выбирайте по задаче.

A · Из агента (Claude Code / Cursor)

MCP-сервер даёт агенту инструменты транскрибации с preflight-проверкой среды; агент оркеструет полный пайплайн (входящие → ASR → хаб → карточки сессий / инсайты) и навыки вроде «обработай свежие записи».

Слой агента (MCP) и кластерный watcher — в дорожной карте репозитория (см. README → Status). Ядро движка ниже (режимы B и C) уже доступно.

B · Из командной строки — один файл

Прямой ASR одного файла; для скриптов и разовых прогонов.

# прямой ASR одного файла
python src\media_transcribe_cli.py --input <media> --output-dir <dir> \
  --model medium --speaker-mode on --timestamps both

# PowerShell-обёртка с явными параметрами прогона
pwsh scripts\run-media-transcribe-direct.ps1 -InputPath <media> `
  -RuntimeDevice cuda -Model medium -SpeakerMode on -ChunkMinutes 20

C · Локальная папка — ручной drop + пакетная обработка

Самый простой режим: складываете медиафайлы в локальную папку и запускаете пакетную обработку — транскрипты появляются в выходной папке. Без хаба, без мультиузла, без агента. Этот режим тоже конфигурируется — но локально: задаёте свои входную и выходную папки.

Конфигурация (локальный срез контракта «источник → приёмник»):

{
  "sources": [ { "root": "C:/work/inbox", "route": "folder", "claim": false } ],
  "outputs": { "transcript_dir": "C:/work/output/{name}" },
  "voiceprint_mode": "off"
  // никаких hub_root / enable_multi_machine — всё локально
}

Запуск (пакетно по всей папке):

# обработать все медиа во входной папке (PowerShell)
Get-ChildItem C:\work\inbox -Include *.m4a,*.mp4,*.wav -Recurse -File | ForEach-Object {
  python src\media_transcribe_cli.py --input $_.FullName --output-dir C:\work\output `
    --model medium --speaker-mode on
}
Подходит для разовой пакетной обработки своих записей без инфраструктуры: бросил файлы в папку → получил транскрипты. Папки — это и есть «конфигурация» локального режима.
Во всех режимах: PYTHONUTF8=1 для кириллицы в выводе; ASR — CUDA-only (fail-fast без GPU).

▶Быстрый запуск (.ps1)

Для регулярной работы есть готовая обёртка scripts/transcribe.ps1 с настройками по умолчанию — не нужно держать в голове флаги CLI. Принимает файл или папку (тогда пакетно).

PowerShell по умолчанию блокирует .ps1. Если «выполнение сценариев отключено» — один раз на сессию: Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass (или запуск через powershell -ExecutionPolicy Bypass -File .\scripts\transcribe.ps1 ...).
# быстрая проверка Inbox (список файлов, без запуска ASR)
.\scripts\transcribe.ps1 -InputPath C:\work\inbox -ListOnly
# один файл
.\scripts\transcribe.ps1 -InputPath C:\work\inbox\meeting.m4a
# целая папка (пакетно по всем медиа)
.\scripts\transcribe.ps1 -InputPath C:\work\inbox -OutputDir C:\work\output
# с параметрами
.\scripts\transcribe.ps1 -InputPath C:\work\inbox\meeting.m4a -Model medium -SpeakerMode on
Скрипт сам берёт venv-python (без активации), выставляет PYTHONUTF8=1, поддерживает файл и папку, переживает ложный exit 9. Параметры по умолчанию: -OutputDir C:\work\output, -Model medium, -SpeakerMode on, -PythonBin C:\work\venvs\asr\Scripts\python.exe — меняйте под себя.

+Мультиузел (несколько машин)

Узлы координируются через Hub файлами .claim.json + heartbeat. Каждому узлу — свой уникальный host_label. Канонический результат (транскрипт + state) всегда в Hub, поэтому машины не зависят от локальных дисков друг друга.

Одна GPU на несколько машин (переключаемая карта). Если видеокарта одна и переезжает между машинами, запускайте watcher только там, где карта сейчас физически подключена. Узел без CUDA честно падает fail-fast и не «застолбит» файл.

🩺Диагностика и обслуживание узла

снять состояние узла одним файлом · обновить узел · починить venv

Когда узел «молчит» (задача зарегистрирована, а транскриптов нет), главная проблема — не нехватка проверок, а доставка их вывода: окно консоли закрывается раньше, чем человек успевает прочитать ошибку, и общего буфера обмена между машинами нет. Поэтому все инструменты ниже пишут результат файлом — локально в репозиторий и в Hub.

Снять состояние узла одним файлом — collect-diag

Самый быстрый способ: двойной клик по scripts\collect-diag.cmd (или запуск .\scripts\collect-diag.ps1 из корня репозитория).

:: двойной клик — либо из PowerShell:
.\scripts\collect-diag.ps1
:: параметры (необязательно): сколько копий хранить и сколько строк лога брать
.\scripts\collect-diag.ps1 -Keep 10 -WatchLogTail 40

Собирает в один файл:

  • git-состояние репозитория (последний коммит + git status -sb);
  • содержимое pyvenv.cfg и версию venv-python (python -V) — та самая причина «No Python at '...'»;
  • путь к ffmpeg (или «NOT on PATH»);
  • env-переменные, на которые ссылается конфиг (env:VAR) — по scope Process / User / Machine, только set/not set, значения не печатаются;
  • scheduled task вотчера: состояние, владелец (UserId + LogonType), последний/следующий запуск;
  • смонтирован ли hub_root под этим пользователем;
  • полный вывод node_diagnostics.py --auto (а если он падает — текст падения);
  • хвост logs\watch.log с его размером и возрастом.

Куда кладёт результат:

:: локально — всегда
<repo>\logs\console-{host}-{YYYY-MM-DD-HHMM}.txt
:: в Hub — если диск смонтирован под этим юзером
{hub_root}\_meta\801-console-{host}.txt              :: последний прогон
{hub_root}\_meta\801-console-{host}-{штамп}.txt      :: история, 10 последних
Зачем именно так: файл в Hub читается с любой другой машины — не нужен буфер обмена между машинами, и не страшно закрывшееся окно консоли. Скрипт только читает: на узле ничего не меняется, секреты не печатаются, а имена env-переменных берутся из конфига, а не захардкожены.

Полная диагностика — node_diagnostics.py

Проверяет CUDA, voiceprint, OCR, ffmpeg, версию кода, вотчер и среду. Запускается любым Python — venv узла он находит сам по полю transcribe_python:

python scripts\node_diagnostics.py
:: без паузы в конце (для планировщика/агента):
python scripts\node_diagnostics.py --auto
:: добавить каталог venv в PATH (лечит Error 103); --machine — для всех юзеров, нужен admin
python scripts\node_diagnostics.py --fix-path
python scripts\node_diagnostics.py --fix-path --machine

Отчёт не только печатается, но и пишется файлами — с штампом времени, чтобы прогоны можно было сравнивать:

ФайлЧто это
{hub_root}\_meta\801-diag-{HOST}.txtпоследний прогон, стабильное имя (перезаписывается) — ссылки и инструкции не ломаются
{hub_root}\_meta\801-diag-{HOST}-{YYYY-MM-DD-HHMM}.txtштамп прогона, история — хранятся 10 последних
<repo>\logs\node-diag-{host}-{штамп}.txtлокальная копия — всегда остаётся на узле, даже если Hub недоступен или окно закрылось (тоже 10 последних; logs/ в .gitignore)
Секция [7] печатает ВЛАДЕЛЬЦА задачи (Principal.UserId + LogonType), а не только юзера текущего прогона, и явно помечает случай, когда владелец задачи ≠ текущий пользователь. Это не косметика: задача видит PATH, venv и смонтированный Google Drive того аккаунта, на который зарегистрирована. Если у него нет примонтированного Hub или рабочего venv — вотчер молчит.
Следствие для установки задачи: install-watch-task.ps1 регистрирует задачу на пользователя того шелла, из которого запущен (-UserId $env:USERNAME). Регистрация требует прав администратора — но elevated-шелл нужно поднимать из-под узлового юзера, а не из-под другой админ-учётки: иначе задача достанется чужому аккаунту. Расхождение лечится пере-регистрацией задачи из admin-шелла нужного юзера.

Обновление узла — update-node.ps1

Приводит узел в актуальное состояние: git pull → синхронизация конфига → линки путей → доустановка недостающих пакетов → диагностика. Рискованное — за явными флагами.

:: код + зависимости + диагностика
.\scripts\update-node.ps1
:: показать план и ничего не делать
.\scripts\update-node.ps1 -DryRun
ФлагЧто делает
-FixVenvчинит venv, чей базовый Python пропал: перенаправляет pyvenv.cfg на живой интерпретатор той же минорной версии и снимает кавычки из путей. Пакеты остаются на месте — torch с CUDA не надо качать заново (бэкап: pyvenv.cfg.bak)
-SyncConfigзаменить config\node.local.json копией из Hub _meta (с бэкапом .bak). Если JSON не парсится или hub_root из Hub-копии на этой машине не резолвится — конфиг откатывается на прежний
-PushConfigобратное направление: выложить рабочий локальный конфиг узла в Hub _meta. Нужен после локальных правок — иначе следующий -SyncConfig их затрёт
-CudaTorchпереустановить torch+torchaudio со сборкой CUDA (-CudaVersion cu128 по умолчанию) и проверить импорт pyannote/speechbrain
-NoDiag / -Auto / -DryRunпропустить диагностику / не ждать клавишу в конце (планировщик, агент) / только напечатать план
Сломанный venv больше не убивает весь прогон. venv проверяется запуском (он может существовать и не стартовать), и шаги, которым venv не нужен — git pull, синхронизация конфига, линки путей — выполняются как обычно. Зависимые шаги (доустановка пакетов, torch, проверки) пропускаются с явной причиной, а диагностика в этом случае гонится системным python.

🗑Удаление узла с машины

снять автозапуск · вычистить окружение · ничего не потерять в Hub

Узел оставляет след в нескольких местах сразу: задача планировщика, возможные записи автозапуска, venv, кэш с голосовыми отпечатками, логи, конфиг, переменные окружения и junction-линки. Вычищает всё это scripts\uninstall-node.ps1 — каждый пункт за своим флагом, и по умолчанию в режиме плана:

:: посмотреть, что будет удалено (ничего не трогает)
.\scripts\uninstall-node.ps1 -All
:: снять только автозапуск: задачи, записи Startup/Run, живые прогоны
.\scripts\uninstall-node.ps1 -Force
:: полная очистка
.\scripts\uninstall-node.ps1 -All -Force
Без -Force не удаляется ничего. Скрипт печатает план со всеми путями — прочитайте его прежде, чем повторять команду с -Force. Порядок именно такой: сначала посмотреть, потом применить.

Что чистится

ФлагЧто удаляет
-Tasksвсе задачи планировщика, чьё имя или действие ведёт на этот вотчер — включая заведённые вручную и под старыми именами
-Autostartярлыки в папке «Автозагрузка» и ключи Run, указывающие на вотчер
-Processesпрогон, идущий прямо сейчас
-Venvдерево venv из transcribe_python
-Cachecache_root — вместе с локальным стором голосовых отпечатков
-Logs<repo>\logs
-Configconfig\node.local.json, его .bak и .last-known-hub
-EnvVarsHF_TOKEN / HUGGINGFACE_TOKEN / HUGGING_FACE_HUB_TOKEN на уровне User и Machine
-Linksjunction/symlink из path_links — только сами линки; реальный каталог по тому же пути скрипт не тронет
-Allвсё перечисленное

Без флагов чистится набор по умолчанию — задачи, автозапуск и живые прогоны: этого достаточно, чтобы узел перестал работать, но данные и окружение остались на месте.

Чего скрипт не трогает

  • Hub — транскрипты, реестры голосов, конфиги узлов в _meta. Это общая работа нескольких машин: снятие одного узла не должно её удалять.
  • Сам репозиторий — скрипт лежит внутри него; папку удаляют вручную, когда всё остальное вычищено.
  • Кэш моделей в профиле пользователя (~\.cache\huggingface) — он общий с другими проектами, чистить осознанно.

Права

Задачу, зарегистрированную другим пользователем, из обычной сессии не видно и не удалить: список задач урезается правами. Скрипт честно скажет «чужая задача — нужен admin-шелл, пропуск» вместо тихого пропуска. Для полной очистки запускайте его из PowerShell от администратора; очистка Machine-переменных тоже требует прав. Подробный разбор — чистка чужих задач.

Проверка после удаления

.\scripts\uninstall-node.ps1 -All        :: повторный план должен быть пустым
Get-ScheduledTask | Where-Object TaskName -match 'watch|transcribe'
Готово, если: план не содержит строк [dry-run] снять и [dry-run] удалить, а поиск задач ничего не возвращает (из admin-шелла).

🔒Приватность

Код публичный — данные приватные. Движок не собирает и не передаёт ваши данные. В репозиторий едут только код, схемы и *.example. Никогда не попадают в репозиторий и в Hub:
  • токены и секреты (credentials.local.json, OAuth-файлы);
  • голосовые отпечатки (_voiceprints/, profiles/*.json) — биометрические ПД;
  • транскрипты, аудио, имена участников, личные пути.

Убедитесь, что .gitignore покрывает: *.local.json, voiceprint-дерево, секреты, медиа и транскрипты.

🍎Вариант: macOS (Apple Silicon)

M-series · CUDA отсутствует → ASR на CPU (int8)

На Mac (M1–M4) нет NVIDIA/CUDA, поэтому движок работает в CPU-режиме. Ниже — дельта от Windows-инструкции; шаги по токенам (4) и идея конфигурации (5) те же.

Главное отличие: здесь нет CUDA/cuDNN/eGPU. Производительность ниже (CPU int8 ≈ 2× реального времени). Ускорители whisper.cpp Metal / MLX — опционально, вне этой инструкции.

1 · Инструменты и код

# Homebrew (если нет) — см. brew.sh; затем:
brew install python@3.11 ffmpeg git
git clone https://github.com/cless75/speaker-transcribe ~/work/speaker-transcribe
cd ~/work/speaker-transcribe

2 · venv + зависимости

python3.11 -m venv ~/work/venvs/asr
source ~/work/venvs/asr/bin/activate     # активировать venv (далее pip/python — из venv)
pip install -U pip wheel setuptools
# torch для macOS — обычная сборка (без cu128; CTranslate2 на Mac работает на CPU)
pip install torch torchaudio
pip install -r requirements.txt
cuDNN и nvidia-cudnn-cu12 на macOS не нужны (это CUDA-стек). ffmpeg ставится через brew.

3 · Токен

huggingface-cli login   # как на Windows (см. шаг 4)

4 · Конфигурация (CPU-профиль)

5 · Запуск и проверка

# прямой ASR одного файла (CPU int8)
python src/media_transcribe_cli.py --input ~/work/recordings/meeting.m4a \
  --output-dir ~/work/output --model medium --speaker-mode on

# локальная папка (batch) — bash:
for f in ~/work/inbox/*.{m4a,mp4,wav}; do
  python src/media_transcribe_cli.py --input "$f" --output-dir ~/work/output --model medium
done
На macOS вывод по умолчанию UTF-8 — PYTHONUTF8=1 не требуется (в отличие от Windows).
